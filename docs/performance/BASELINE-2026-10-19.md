# Performance baseline - 2026-10-19 (Day 42, ADR-0037)

A first, small measurement of the running system, so later changes have something to be compared with.
It is **not** a capacity statement and **not** a pass/fail test: no targets exist yet, so none of these numbers
is "good" or "bad" on its own. Re-run with `bash build/scripts/perf-baseline.sh` on an idle machine.

## What was measured

Real docker-compose stack (Gateway, Api, PostgreSQL, RabbitMQ, plus the observability stack), load generated by
k6 from inside the compose network, going through the Gateway. Three paths, each held at 1, 10, 25 and 50
virtual users for 30 seconds, one level at a time (with a 5 s gap), after a short warm-up:

| Path | Request | What it exercises |
|---|---|---|
| `health` | `GET /health` | Gateway to Api proxy cost only: no auth, no database |
| `read` | `GET /api/reference/countries/IN` (JWT) | JWT validation at Gateway and Api, one PostgreSQL read |
| `write` | `POST /diagnostics/widgets` | one PostgreSQL write, then one RabbitMQ publish (and the consume, asynchronously) |

Each virtual user sends its next request as soon as the last one returns (closed loop, no think time). The
Gateway rate limit was raised to 1,000,000 per 10 s for this run, so the limiter did not interfere (0 responses
were 429). Its default (100 per 10 s per client IP) is unchanged.

## What the numbers show

- **Unloaded cost (1 user):** health 3.4 ms median, read 9.0 ms, write 16.2 ms. Reading a row costs about 6 ms
  more than a bare proxied call; writing and publishing an event costs about 13 ms more.
- **health and read scale smoothly.** Throughput rises with users (health 183 to 1,107 rps, read 88 to 536 rps)
  while latency grows roughly in proportion; p95 stays under 170 ms at 50 users.
- **write stops scaling early.** Throughput is about 136 rps at 10 users and only 177 rps at 50, so extra users
  mostly add waiting: median latency rises from 61 ms to 206 ms, p95 jumps from 116 ms (10 users) to 735 ms
  (25 users), and p99 reaches about 2 s. Maximum latencies of 1.2 to 2.1 s appear from 10 users up.
- **Resources during the run** (sampled every 5 s over the whole run, so a peak cannot be tied to one level):
  highest CPU seen was RabbitMQ about 298%, Api 228%, Gateway 173%, Tempo 138%, k6 120%, PostgreSQL 86% (100% is
  one core; Docker had 8). Peak memory: Api 365 MiB, RabbitMQ 216 MiB, Gateway 131 MiB, PostgreSQL 125 MiB.

## Observations that are not conclusions

- **Write-path cause: followed up on Day 45** (`WRITE-PATH-2026-10-19.md`, ADR-0040). Traces showed the RabbitMQ
  publish step was the cost (a channel opened, the exchange declared and the channel closed on every publish);
  reusing one channel about doubled write throughput at 25 users and removed the multi-second tail. The numbers
  in the tables above are the **original** measurement, before that fix. The same follow-up measured run-to-run
  variation of about 25 to 30% on this machine, which this report had listed as unknown.
- Tracing, metrics and log shipping were all on, which is how the stack runs in development. Their cost is
  included in every number and was not separated out.

## Limits of this baseline (read before comparing against it)

- **One run, 30 seconds per level.** Run-to-run variation was later measured at about 25 to 30% (Day 45); a difference of a few percent between two
  runs means nothing. Repeat before trusting a small change.
- **One machine, everything on it.** A Windows laptop under Docker Desktop (8 CPUs and 7.6 GiB for all
  containers), with k6, the application, the database, the broker and the observability stack competing for the
  same cores. A real deployment would separate them.
- **Development configuration**, Release builds, a single Api instance, a single PostgreSQL with default
  settings, an almost empty database (the write test grows it by a few thousand rows).
- **Closed-loop load**: users wait for each reply. It shows behaviour as concurrency rises, not what happens when
  requests arrive faster than they can be served.
- **Three paths only.** The rules-engine evaluation (the heaviest path built so far), login, the audit and
  notification paths, and the Api without the Gateway were not measured.
- **Not tied to the PRD.** PRD Ch. 1.3 mentions 500,000 shipments a day and Ch. 3.5 has SLA targets per stage.
  Nothing built yet maps onto them, so no judgement is made here.

## Reproducing

```bash
bash build/scripts/perf-baseline.sh                      # full run, about 8 minutes including the image build
PERF_STEADY_SECONDS=10 PERF_VU_LEVELS=1,10 bash build/scripts/perf-baseline.sh   # quick check
```

Results are written to `TestResults/perf/` (git-ignored): `baseline-table.txt`, `baseline-rows.json`, the raw
`k6-summary.json`, `docker-stats.csv` and `environment.txt` (machine, commit, settings). Close other Docker
stacks and heavy programs first; the run records how many other containers were running.
